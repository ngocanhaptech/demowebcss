One path, from words to a running system

Every workflow in Kiln moves through the same five stops. You can inspect, pause, or edit at any of them — nothing runs as a black box.

  • You describe the outcome
  • Agent drafts the steps
  • Steps call real tools & files
  • Preview, then deploy

How a workflow gets built

  1. 1

    Describe the outcome

    Write the result you want in plain sentences. No flowchart, no config file — Kiln asks follow-up questions if something is ambiguous.

  2. 2

    Review the draft

    The agent proposes each step it plans to take and which tools or files it needs access to. You approve, edit, or remove any step before it runs.

  3. 3

    Preview on real data

    Run the workflow against a small, real sample — not synthetic fixtures — so you see the actual output before anyone else does.

  4. 4

    Deploy with a rollback path

    Ship the version you previewed. Every deploy keeps the previous version one click away.

Built for how engineering teams actually ship

Every run is inspectable

See exactly which files, APIs, and records a workflow touched — before and after it runs. Nothing executes silently.

Versioned by default

Every edit creates a new version. Roll back without redeploying by hand.

Scoped access per workflow

A workflow only gets the tool and file permissions it was granted — not your whole workspace.

Pause on error

A failed step stops the run and notifies the owner instead of continuing partway.

Shared components

Reuse a step — like "send Slack message" — across workflows instead of rebuilding it.

Trigger it from code, not just the UI

Every workflow gets an endpoint. Call it from a cron job, a webhook, or your own backend.

  • REST API and typed SDK
  • Signed webhook triggers
  • Self-hosted or managed deploy
run-workflow.sh 
curl -X POST https://api.kiln.dev/v1/workflows/onboarding/run \

  -H "Content-Type: application/json" \
  -d '{"employee_id": "e_2291"}'

Encryption in transit and at rest

Workflow data is encrypted end to end between your tools and Kiln's runners.

Workspace isolation

Each workspace runs in its own execution boundary — no shared runtime state between customers.

Retention controls

Set how long run history and logs are kept, per workspace.

Audit log

Every run, edit, and permission change is attributed to a person and timestamped.
